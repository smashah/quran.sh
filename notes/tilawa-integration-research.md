# Tilawa integration research

Checked 2026-07-21 against Tilawa's repository at `ec5cdc7`, its npm package and release assets, and OpenTUI `0.4.5` audio documentation and source.

## Verdict

Tilawa can power an optional **listen-to-my-recitation** mode in quran.sh, but it is not a recitation player or an audio catalogue. It accepts 16 kHz mono PCM, runs an ONNX speech-recognition model locally, and emits verse matches and word progress. OpenTUI solves the opposite half—audio output and encoded MP3/FLAC streaming—but exposes no microphone/capture API, so a live Tilawa feature needs a separate capture adapter. [Tilawa README](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/README.md), [OpenTUI native-audio guide](https://github.com/anomalyco/opentui/blob/v0.4.5/packages/web/src/content/docs/core-concepts/audio.mdx), [OpenTUI audio API](https://github.com/anomalyco/opentui/blob/v0.4.5/packages/core/src/audio.ts)

Keep playback and recognition as separate application services. Known ayah playback does not need speech recognition, while microphone recognition should not depend on the playback engine or accidentally listen to quran.sh's speakers.

## Package, assets, and runtime compatibility

The current install is `bun add @tilawa/core@0.1.0 onnxruntime-node`. `@tilawa/core` is ESM, pure TypeScript, has no runtime dependencies or engine declaration, and deliberately requires the application to inject a `SessionRunner`; the reference Node adapter uses `onnxruntime-node`. The npm package and model release have independent version numbers: npm has only `@tilawa/core@0.1.0`, while the current model/content bundle is GitHub release `v0.2.0`. Pin both explicitly rather than treating them as one release train. [core package manifest](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/packages/core/package.json), [Node runner](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/packages/core/examples/session-node.ts), [v0.2.0 release](https://github.com/yazinsai/tilawa/releases/tag/v0.2.0)

The `v0.2.0` assets total 103,982,532 bytes (99.2 MiB): an 88.3 MB ONNX model, 12.2 MB CTC token table, 3.19 MB Quran JSON, and small vocabulary, tokenizer, and metadata files. Inference needs the model, `vocab.json`, `quran_ctc_tokens.json`, and `quran.json`; `export_metadata.json` supplies hashes and the blank-token ID. The model consumes raw mono 16 kHz `Float32Array` audio and returns `[1, timeSteps, 1025]` CTC log probabilities. [release asset API](https://api.github.com/repos/yazinsai/tilawa/releases/tags/v0.2.0), [release metadata](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/web/frontend/public/export_metadata.json), [`SessionRunner` contract](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/packages/core/src/session.ts)

Tilawa officially documents Node, web, and React Native, not Bun. A local compatibility probe on 2026-07-21 successfully imported `@tilawa/core@0.1.0` under Bun `1.3.14` and Node `26.4.0`, then created an `onnxruntime-node` session and ran two seconds of silent audio under Bun on macOS arm64. That is encouraging, but `onnxruntime-node` is a native dependency and must be tested on every quran.sh OS/architecture and in standalone builds before Bun support is claimed. The 99 MiB model should remain a post-install download rather than being embedded in the normal CLI binary.

## API and recognition timing

`createTilawaSession(runner, assets, options)` returns `transcribe`, `transcribeRaw`, `feed`, `reset`, `setConfig`, `getConfig`, `db`, and `decoder`. One-shot `transcribe` returns `{surah, ayah, ayah_end, score, transcript}`, using zero values when no match passes the internal trust threshold. Streaming `feed` both returns messages and calls `onOutput`; quran.sh should consume one path, not both, to avoid duplicate state updates. [public API implementation](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/packages/core/src/index.ts)

The useful streaming messages are:

- `verse_candidate` is provisional ranking and should update a listening status row without navigating.
- `verse_match` is a committed verse with confidence and surrounding verses; this is the safe navigation event.
- `word_progress` gives word indices and matched indices for highlighting, but no timestamps.
- `final_sequence` summarizes the ordered verses after the utterance is flushed.

The default balanced configuration expects roughly 150 ms input chunks, starts discovery after 2 seconds of accumulated audio, reruns tracking after 250 ms of new audio, retains up to 30 seconds during discovery and 12 seconds while tracking, and finalizes after 1.2 seconds of silence. Each `feed()` is asynchronous and inference runs against a retained window, so calls must be serialized off the TUI/render thread. High-level messages contain confidence and word positions rather than sample timestamps, which means Tilawa cannot provide exact seek/progress timing for prerecorded recitation playback. [streaming types and presets](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/packages/core/src/types.ts), [tracker feed loop](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/packages/core/src/tracker.ts)

## Capture, playback, streaming, and caching boundaries

**Microphone capture:** Tilawa's browser demo uses `getUserMedia` plus an `AudioWorklet` that down-samples the first channel to 16 kHz and posts configured chunks to a worker. OpenTUI `Audio` only lists playback devices and exposes output mixing/taps; it has no recording or input-device API. quran.sh therefore needs an application-owned `AudioCapture` interface that yields mono 16 kHz chunks, with platform implementations selected separately. OpenTUI's master tap contains quran.sh's mixed playback output, not microphone input, so it is useful for a playback level meter but is not the capture solution. [Tilawa browser capture](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/web/frontend/src/main.ts), [capture worklet](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/web/frontend/public/audio-processor.js), [OpenTUI audio API types](https://github.com/anomalyco/opentui/blob/v0.4.5/packages/core/src/audio.ts)

**Playback:** Tilawa contains no reciters and serves no recitation audio. quran.sh must choose and license a recitation provider independently. OpenTUI can load complete encoded sounds or progressively play URL/byte streams in MP3 or FLAC, exposes buffering/decoded/played-frame statistics, and emits `ended`, `error`, and `disposed`; it does not expose pause, seek, duration, voice-completion, or a range-aware seek abstraction in `0.4.5`. Per-ayah files fit that API better than a single surah file requiring seeks. `framesPlayed / sampleRate` can drive a coarse elapsed indicator, but provider timing data is required for word-accurate highlighting. [OpenTUI sounds and streams](https://github.com/anomalyco/opentui/blob/v0.4.5/packages/web/src/content/docs/core-concepts/audio.mdx)

**HTTP streaming/ranges:** Tilawa itself performs no audio fetch and has no HTTP Range support; its “streaming” means incrementally feeding PCM into recognition. OpenTUI URL streaming fetches sequential MP3/FLAC bytes with bounded buffers and cancellation/reconnect support. Although request headers can be supplied, there is no released seek API that maps a playback position to byte ranges, so quran.sh should not promise resume or scrubbing around `playStreamUrl()`.

**Offline/cache:** `@tilawa/core` does no downloading or caching. Once the model and JSON assets are local, inference requires no network. Tilawa's web example caches only the model in IndexedDB; its text assets are fetched at initialization, and its service worker currently deletes service-worker caches and unregisters itself. For the CLI, quran.sh must own a versioned asset directory, explicit download consent/progress, SHA-256 verification, atomic writes, disk-space checks, a remove-model command, and offline startup from verified files. [model cache](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/web/frontend/src/worker/model-cache.ts), [worker initialization](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/web/frontend/src/worker/inference.ts), [service worker](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/web/frontend/public/sw.js)

## Licensing and maintenance risk

Tilawa's code and npm package are MIT licensed. Its README identifies the ONNX model as Cyberistic's `c2c-direct-mixed-tta`, based on NVIDIA's Arabic FastConformer, and states the model license is CC-BY-4.0; quran.sh must preserve the required model attribution. The repository does not document independent provenance or redistribution terms for `quran.json` and the derived CTC token table, so bundling those assets inside release binaries should wait for maintainer clarification even though downloading them directly for a user's local cache is technically straightforward. [Tilawa license](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/LICENSE), [model attribution](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/README.md), [release metadata source field](https://github.com/yazinsai/tilawa/blob/ec5cdc72c1c48ba29866ca2e3197d6b9a0e2e793/web/frontend/public/export_metadata.json)

The project is active but very young: it was created in February 2026, published model releases in March and June, extracted/published the npm SDK in July, and last pushed code on 2026-07-09. GitHub reports it as unarchived with one open issue, but npm has only one package release and development is concentrated around one maintainer. Treat both the SDK and model contract as pre-stable: pin versions and hashes behind a quran.sh adapter, add fixture-based compatibility tests, and avoid exposing Tilawa types throughout the UI. [repository metadata](https://api.github.com/repos/yazinsai/tilawa), [releases](https://api.github.com/repos/yazinsai/tilawa/releases), [npm package](https://www.npmjs.com/package/@tilawa/core/v/0.1.0), [commit history](https://github.com/yazinsai/tilawa/commits/main/)

## Phased quran.sh architecture

1. **Ship recitation playback without Tilawa.** Add a `RecitationPlayer` around OpenTUI `Audio`, use per-ayah MP3/FLAC URLs from a separately reviewed provider, and expose loading/buffering/playing/ended/error state plus volume and stop/restart. Keep the player outside React and subscribe UI state to it, so render lifecycles do not own native resources.
2. **Add an optional recognition asset manager.** On the first `listen` command, explain the approximately 99 MiB download and model attribution, then fetch the pinned Tilawa `v0.2.0` files into a versioned cache with checksums and atomic promotion. Do not enlarge the default binary or silently download on startup.
3. **Prove the runtime seam before UI work.** Put `@tilawa/core`, `onnxruntime-node`, asset parsing, and the `SessionRunner` behind a `TilawaRecognizer` adapter. Run one-shot fixture tests under Bun on every shipped platform and standalone target, then test streaming in a worker so ONNX inference cannot stall OpenTUI input/rendering.
4. **Build microphone capture as its own boundary.** Define `AudioCapture.start(): AsyncIterable<Float32Array>` with an explicit 16 kHz mono contract, permission/error states, and deterministic disposal. Select and audit platform backends separately; this is the blocking dependency because neither Tilawa core nor OpenTUI records audio.
5. **Add a conservative listening UI.** `verse_candidate` updates a low-key candidate label; only `verse_match` changes the selected surah/ayah; `word_progress` highlights words in the text reader; `final_sequence` records the session summary. Provide confidence thresholds, a manual correction path, a clear recording indicator, and immediate stop/reset.
6. **Harden before enabling by default.** Test noisy rooms, different reciters, short ayat, Bismillah boundaries, device loss, slow inference, cancellation during download/inference, cache corruption, and playback/microphone feedback. Keep recognition opt-in until accuracy and CPU/memory costs are measured on quran.sh's supported hardware.

The key product boundary is simple: OpenTUI plays recitation, Tilawa recognizes live PCM, and quran.sh owns capture, content licensing, caching, orchestration, and UI state. The microphone adapter and asset provenance are the two blockers to implementation; the TypeScript SDK itself is the straightforward part.
