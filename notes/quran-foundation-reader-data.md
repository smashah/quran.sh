# Quran.com reader data and interaction inventory

Checked 2026-07-21 against the live [Quran.com Al-Fatihah 1:3 page](https://quran.com/al-fatihah/3), Quran Foundation's current API documentation and Developer Terms, and first-party repositories in the [`quran` GitHub organization](https://github.com/quran).

## Verdict

Quran Foundation's documented APIs cover almost the whole Quran.com reading surface: multiple Arabic scripts, word-by-word text and audio, translations and footnotes, tafsir, recitations and timing, navigation coordinates, surah metadata, hadith, Q&A, lessons/reflections, search, and account-backed reading state. They are the best authoritative online source, but they are **credentialed application APIs rather than a distributable open corpus**. A shipped CLI must not embed the required client secret, and normal QF Content may not be cached for more than one week without express permission.

The clean first-party offline exception is [`quran/quran-tajweed`](https://github.com/quran/quran-tajweed), whose generated Hafs tajweed annotation JSON is explicitly CC BY 4.0. Qirāʾāt and related-verse data appear in Quran.com's public UI and frontend source, but no corresponding endpoint is present in the documented API reference; they should remain research prototypes until Quran Foundation documents and licenses access.

## Source classes

| Class | What belongs here | Production posture |
|---|---|---|
| Stable public/open | A repository or artifact with an explicit reusable license | May be bundled or cached within that license, with pinned versions and attribution |
| Credentialed official | Documented Content, Search, or QuranReflect API operations | Apply for access; use only through an approved secret-safe architecture; honor the seven-day default cache limit |
| Auth/user-private | OAuth-scoped Quran.com account data | Optional sync only, after consent, token security, privacy policy, revoke/delete flows, and conflict semantics exist |
| Brittle internal | Paths visible in Quran.com's frontend but absent from the API reference | Do not ship against them; source inspection proves the web feature exists, not that third-party access is supported |
| External/provider-owned | Content attributed to authors, reciters, publishers, Tanzil, King Fahd Complex, or separate ecosystem sites | Preserve resource attribution and the provider's license; QF's repository or API is not a blanket relicensing grant |

## Legal, caching, and authentication boundary

The [QF Developer Terms](https://api-docs.quran.com/legal/developer-terms/) define Quran text, translations, metadata, audio, reflections, and other API responses as “QF Content.” They permit display as an integral part of an end-user Quranic experience, require Quran text to remain unmodified, prohibit resale/sublicensing/raw redistribution, and prohibit scraping or indexing outside API responses. They also prohibit storing QF Content longer than one week unless expressly permitted. This means:

- A refreshable SQLite cache with `fetched_at`, `expires_at <= 7 days`, source/resource IDs, and purge-on-termination behavior is feasible. A permanent bundled QF corpus or downloadable community “content pack” is not, unless QF grants written permission.
- The official [Content Sync offline-cache pattern](https://api-docs.quran.com/docs/tutorials/content-sync/offline-cache-patterns/) is useful for atomic snapshots, local-first reads, idempotent changes, and recovery, but it does not override the Terms' retention limit. Refresh or expire cached content within seven days.
- Content APIs use `client_credentials` and require `x-auth-token` plus `x-client-id`. The [official quickstart](https://api-docs.quran.com/docs/quickstart/) says the client secret belongs on a backend, never in browser/mobile code; the same constraint applies to a distributed Bun executable. Ask QF for an approved native/CLI client shape. If none exists, use a quran.sh-controlled proxy or keep the existing open provider for the offline core—never compile a shared QF secret into the CLI.
- [API access must be requested](https://api-docs.quran.com/request-access/) and is subject to revocation and deprecation. Store no rate-limit assumptions as constants, and make QF-backed panels degrade independently when unavailable.
- The Terms do not give a blanket open license for each translation, tafsir, recitation, font, or hadith. Display the API's `resource_name`, author, reciter, language, and style metadata in the TUI and retain them in cache records; seek separate permission before exporting or redistributing a resource.

### Rendering requirements inherited from the API

Translation and tafsir bodies may contain HTML and footnote markers. Parse to an allowlisted intermediate model (`text`, paragraph, heading, list, emphasis, footnote reference), strip everything else, and escape terminal control sequences before rendering. Quranic Arabic must remain byte-for-byte unmodified in storage and selection/copy paths; visual bidi isolation belongs in the renderer, not in persisted text.

## Authenticated user-private interactions

The [User API reference](https://api-docs.quran.com/docs/category/user-related-apis-1.0.0/) includes bookmarks, collections, comments, goals, notes, posts, preferences, reading sessions, activity days, rooms, streaks, tags, and users. The [OAuth quickstart](https://api-docs.quran.com/docs/tutorials/oidc/user-apis-quickstart/) requires a user session, and the [scope catalog](https://api-docs.quran.com/docs/user_related_apis_versioned/scopes/) requires consent for only the approved scopes a feature needs.

| Private feature group | Data/interaction | Offline and privacy posture | TUI experience |
|---|---|---|---|
| Bookmarks, collections, tags | Saved verses, organization, collection membership | Keep quran.sh local-first. Optional sync needs OAuth, stable remote/local IDs, an outbox, tombstones, and visible conflict resolution | Bookmark key, named reading lists, tags/filtering, sync state per item |
| Notes | Private/published notes associated with verses | Religious notes are sensitive personal data. Encrypt local secrets/tokens, never log bodies, request only `note` scopes, and provide export/delete | Markdown/plain-text verse notes, private by default; publishing is a separate explicit action |
| Reading sessions, activity days, goals, streaks | Reading progress and derived activity | Local history works without an account. Cloud sync requires explicit consent, minimal retention, and no advertising/AI reuse | Resume position, daily goal, session timer, streak/calendar, estimated reading plan |
| Preferences | Reading mode, selected translations/tafsirs, script/font scales, word display/click behavior, reciter, playback rate, auto-scroll and repeat settings | Store locally by default; sync only `preference` after login. Do not silently overwrite device-specific terminal choices | A profile that follows the user while terminal capability overrides stay local |
| Profiles, rooms, posts, comments, follows | Social QuranReflect identity and engagement | Highest privacy/moderation complexity. Defer until the CLI has a public privacy policy, revocation, deletion, abuse reporting, and secure hosted OAuth callback | Later opt-in social feed; not part of the core reader |

The [Developer Privacy Policy requirements](https://api-docs.quran.com/legal/developer-privacy/) treat religious activity as sensitive data and require data minimization, explicit consent, TLS/encryption, scope revocation, deletion, retention disclosure, and incident handling. Those obligations make account sync a separate product milestone, not a side effect of adding bookmarks.

## External and provider-owned boundaries

- [`quran/quran-tajweed`](https://github.com/quran/quran-tajweed) derives its offsets against a specific [Tanzil](https://tanzil.net/download/) Uthmani text. The annotation file is CC BY 4.0, but the base text retains Tanzil's own license and exact-codepoint requirements. Attribute both when they are distributed together.
- Quran.com's footer links QuranReflect, Quran.ai, Sunnah.com, and Corpus.Quran.com. A link or common ecosystem branding is not an API license. Use QF's documented QuranReflect and Hadith operations; do not scrape the other sites.
- Translation, tafsir, and recitation resource metadata names the author, publisher/resource, reciter, language, and style. Preserve those fields in every display/export. If a future resource advertises its own license, obey both that license and QF's API Terms.
- The King Fahd Quran Complex fonts/pages referenced by `quran.com-images` are provider-owned. Repository availability does not authorize repackaging.
- The project's existing [`quran-json`](https://github.com/risan/quran-json) source, QUL/Tarteel datasets, and Tilawa recognition services are external to Quran Foundation. Evaluate them under their own notes/licenses and never label their data as Quran.com data.

## Recommended implementation sequence

1. **Keep the offline reader independent.** Preserve an openly licensed local Arabic/translation source for startup and offline reading. Add the CC BY 4.0 tajweed annotations only after an exact base-text hash fixture proves all 6,236 verse strings and codepoint offsets align.
2. **Ask QF for the CLI architecture before coding the adapter.** Request Content/Search access and a sanctioned native/public-client design. If QF requires a confidential client, put `@quranjs/api` behind a small quran.sh proxy; do not accept a checked-in or compiled secret.
3. **Add one namespaced cache and provenance model.** Key records by provider, API family/version, resource type/ID, verse key, language, and reciter/mushaf where relevant. Store attribution, source URL, fetched/expiry timestamps, ETag/version, and content hash; enforce the seven-day QF ceiling centrally.
4. **Ship the high-value read-only slice first.** Scripts/word data, translations+footnotes, tafsir, recitation+timing, surah metadata, and navigation coordinates produce the Quran.com-like reader without user privacy or unsupported endpoints. Fetch study panels lazily and let each fail independently.
5. **Add contextual official panels second.** Hadith, Answers, and verified QuranReflect lessons/reflections should be lazy, attributed, cursor-paginated, and separately cacheable.
6. **Defer account sync and internal-only features.** Local bookmarks/notes/goals remain useful now. QF OAuth sync waits for consent/revoke/delete/security work; qirāʾāt and related verses wait for documented endpoints or independently licensed datasets.

The implementation boundary that matters most is provider provenance: a verse can combine open local Arabic, CC BY tajweed offsets, a credentialed QF translation, QF-timed audio, and a private user bookmark. Store and render those as separate namespaced records so licensing, expiry, attribution, and deletion rules remain enforceable rather than collapsing them into one opaque verse object.
